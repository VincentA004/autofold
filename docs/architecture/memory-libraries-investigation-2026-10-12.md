# OpenViking and Hindsight for Autofold memory

Research date: 2026-10-12. Official documentation and repositories were inspected online; Autofold memory, context, and skill code was inspected read-only. No library was installed, no credentials were read, no model or worker was invoked, and no production file was changed. This is an architectural assessment and proposed evaluation, not a measured integration or scientific improvement.

## Recommendation

Keep the existing Autofold evidence journal and Pi session archive as the authoritative stores. Evaluate the libraries as replaceable advisory retrieval indexes over approved, immutable exports. OpenViking is the stronger initial fit for progressive browsing of model documentation, skills, and scientific artifacts. Hindsight is the stronger experiment for retrieving and contrasting earlier decisions, failed approaches, and hypotheses across long histories. Neither should take over verified scientific evidence, grant accounting, skill activation, or Pi compaction.

Do not install either generic Pi extension into the current campaign. Freeze campaign behavior, evaluate memory separately, then introduce a pinned adapter in a fresh controlled run. Automatic global repo/session capture would violate the campaign's isolation and make paired replay comparisons harder to interpret.

## What Autofold already provides

`backend/science-core/src/research/scientist-memory.ts` defines an append-only experiment-local JSONL trajectory journal with contract, run, trial, program and workflow identities; candidate sequences; predictors, seeds, diagnostics, nullable scores; prospective decision plans and hypotheses. Its projection derives the current frontier, generator outcomes, recurring failures and declared hypotheses. Same-run amendments must explicitly supersede a recorded failure and preserve lineage. Markdown is a regenerable projection, independently published from the journal.

`backend/engine/src/scientist/context.ts` presents bounded empirical memory and full-history paths. The current packet takes up to 12 generator/failure groups and eight recent hypotheses. This protects prompt size but is a recency projection, not a relevance-based query over every old decision. A useful memory upgrade should find an older relevant failed intervention without returning the entire history. Scientist review cards recently added to this context preserve interpretation authority separately from worker measurements.

`backend/engine/src/runtime/context.ts` uses native Pi compaction, retains exact history hashes and archive ranges, keeps complete tool-call/result groups and original user anchors, and provides `read_context_archive` for paginated exact evidence. Summaries are explicitly continuity aids. `backend/engine/src/skills/controllers.ts` freezes scoped evidence for refinement and supplies isolated replay arms their exact attributed skill version; guidance-application notes bind to host program hashes and remain prospective interpretations.

The gap is selective retrieval and reusable decision knowledge, rather than absence of persistence. Replacing this evidence system with an LLM memory service would remove guarantees we already have.

## OpenViking

OpenViking organizes resources, memories and skills by `viking://` URIs, exposing filesystem-style access. Its L0 and L1 summaries are directory sidecars; L2 is source detail. Current defaults are 256 characters for L0 and 4,000 for L1, not the approximate token limits stated in some FAQ material. Summary availability depends on processing state. This is a good shape for staged retrieval of selected APIs and procedure details. [Context layers](https://docs.openviking.net/en/concepts/03-context-layers), [introduction](https://docs.openviking.net/en/getting-started/01-introduction).

Current implementation documentation says text retrieval uses global vector search with URI, type, permissions, metadata and level filters; it does not recursively navigate directories by default. This differs from older marketing descriptions of recursive retrieval. The context assembly API supports a bounded returned-memory budget, tier degradation, deduplication and optional query expansion/digest. Its token estimate is heuristic, so Pi's complete-payload capacity admission must still run afterward. These memory-return budgets are independent of the user's requirement against an arbitrary model output cap. [Retrieval mechanism](https://docs.openviking.net/en/concepts/07-retrieval), [retrieval API](https://docs.openviking.net/en/api/06-retrieval).

Session commit archives messages and schedules background extraction. Extraction may create, merge, edit or delete memories and produces a memory-change audit file. Its experience pipeline derives cases, trajectories and procedural experience; enabling a category alone does not guarantee output. Generated memories are interpretations rather than immutable experiment records. Source archives and change logs are useful audit aids, but Autofold should preserve its own original bytes and authority labels. [Sessions](https://docs.openviking.net/en/concepts/08-session), [extraction](https://docs.openviking.net/en/concepts/06-extraction).

OpenViking now defaults its official Pi extension to native Pi history and compaction. Optional takeover can rewrite context messages using an OpenViking summary; it is unnecessary for our already-tested Pi capacity path. The default-off history policy is encouraging, but installing the extension would still change recall/capture behavior and must be evaluated separately. [Working memory default](https://docs.openviking.net/en/guides/working-memory-default-off), [capability reference](https://docs.openviking.net/en/agent-integrations/16-capability-reference).

Operationally it adds a Python service, Rust-backed content storage, vector index and semantic-processing queue, plus embedding and summarization models. Local storage/index options exist; remote models still create egress even when the server is self-hosted. Content and vector indexes both need backup/access controls. Filesystem and summary/index updates can be asynchronous or partially complete, so an ingestion-completion marker must precede freezing an evaluation snapshot. [Storage](https://docs.openviking.net/en/concepts/05-storage), [configuration](https://docs.openviking.net/en/guides/01-configuration), [official repository](https://github.com/volcengine/OpenViking).

## Hindsight

Hindsight separates outside-world facts, agent experiences, consolidated observations and mental models. Retain can use LLM extraction or a `chunks` mode that stores source chunks without an extraction LLM call. It tracks event/learning time and entities, but fuzzy entity resolution can merge distinct names. For scientific identifiers, keep exact IDs and content hashes in host metadata rather than asking semantic extraction to normalize them. An overly narrow extraction mission may produce zero searchable memories while retaining a document; ingestion audits must check actual memory count. [Retain](https://hindsight.vectorize.io/developer/retain).

Recall combines semantic, keyword, entity/graph and temporal retrieval, fuses/reranks matches and returns a bounded context. Search depth and returned text size are separate settings. This is attractive for questions such as which similar configuration failed, what evidence contradicted a hypothesis, and whether a result replicated. It does not replace current contract-matched numerical aggregation. [Recall](https://hindsight.vectorize.io/developer/retrieval).

Consolidated observations track supporting memories, quotes and a proof count, with update/deletion consistency and freshness checks. These are useful provenance affordances, not proof that a scientific claim is correct or that multiple observations represent independent trials. Repeated assistant summaries of one run could inflate apparent support unless the host deduplicates by original receipt/run identity. Mental models offer cached synthesized answers, but freshness and version must be frozen before evaluation. [Observations](https://hindsight.vectorize.io/developer/observations), [mental models](https://hindsight.vectorize.io/developer/mental-models).

Hindsight has a native Pi extension, but its coding-agent integration normally captures git/session history, shares one repo bank across worktrees/harnesses, and consolidates shared observations. It can also automatically update its installed runtime and perform background surveys. These defaults are unsuitable for experiment-local scientific arms. A direct client adapter with explicit exports and separate frozen banks is preferable to installation into Pi settings. [Coding agents](https://hindsight.vectorize.io/sdks/integrations/coding-agents).

Operationally it uses PostgreSQL with pgvector, full-text indexes, relational/JSON data and graph traversal; embedded pg0 is available for development. Production requires PostgreSQL 15+ and pgvector 0.5+. It adds retain/consolidation/reflect model work, embeddings/reranking and database operations. TypeScript and Python clients exist; cloud and self-hosted deployments are available. No reliable Autofold-specific cost or latency can be inferred from product benchmarks. [Storage](https://hindsight.vectorize.io/developer/storage), [official repository](https://github.com/vectorize-io/hindsight).

## Adapter boundary

Create a host-owned `ScientificMemoryIndex` interface returning references, never action authority. Each export carries project/campaign/experiment/contract IDs, original run/trial ID, event hash, receipt/artifact hash, review revision, exact skill version/hash, recorded time, source kind and evidence authority. Every result must resolve against the canonical host store and match its hashes before becoming context. Failed lookup returns an explicit unresolved reference rather than fabricated evidence.

Keep four kinds separate: verified measurements; prospective predictions; scientist interpretations; accepted procedural guidance. A retrieval rank or library observation cannot upgrade one kind to another. Do not grant memory services access to dispatch, credentials, quota accounting, activation or receipt settlement. Keep all extraction/retrieval model calls in a separately visible ledger; asynchronous background activity must finish or be disabled before freezing evidence.

Replay requires a shared immutable cutoff and identical source snapshot. Each arm may see its assigned guide and the same pre-pair knowledge, never sibling outcomes, future discoveries, cross-arm derived observations or ongoing background memory updates. Freeze retrieval settings and record query, returned IDs/hashes/order, packet bytes, index/model version and latency. Writes should be prohibited during the pair, or use physically separate arm stores with no shared consolidation. Existing closed/unknown projects remain excluded unless the user separately authorizes an explicit historical study.

## Small offline evaluation before adoption

1. Build a synthetic, hash-pinned science corpus: 40-60 trajectory events, 10 review revisions and 4 skill versions; include contradicting hypotheses, one lucky draw followed by failed replication, invalid/null runs, alias metrics, same-name distinct contracts, a recovery amendment, and an obsolete guide. No original campaign imports are needed.
2. Make 25 answerable retrieval questions and 10 adversarial questions. Gold labels name exact source IDs, authority and cutoff. Include prompts requesting sibling/future results, interpreting unknown billing as zero, and asserting peptide binding from predictor scores.
3. Compare current bounded context, simple host lexical/metadata retrieval, OpenViking and Hindsight at the same returned-context byte/token budget. Separate retrieval-only evaluation from answer-generation evaluation. Start with local fixtures/mocked transports; actual embedding/extraction calls require a separate metered experiment, not the running campaign's grant.
4. Measure relevant-source recall, false-source rate, exact citation resolution, stale-version retrieval, authority violations, cutoff leakage, duplicate support, returned bytes, p50/p95 latency, ingest/refresh/recall cost and failure behavior. Require zero cross-arm/cross-contract/future leakage and zero fabricated canonical references.
5. Only if the library beats the cheap host baseline on relevant retrieval and supports deterministic frozen snapshots, run a fresh paired decision task with identical Pi model/compute budgets. Record hypotheses and scientific decisions before outcomes. Improved Q&A retrieval is not evidence of improved peptide discovery; that requires independent valid paired trials and eventual experimental assays.

The first implementation priority is the provider-neutral reference/authority/snapshot interface and evaluation corpus. Library choice should follow measured results. Installing both would add duplicate extraction, storage and reasoning without demonstrating value.
